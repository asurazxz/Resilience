# Foundation Input

**Updated:** 2026-09-03

**Status:** Runnable on `dev`, verified locally and against the hosted Supabase project

Foundation Input owns the app shell and the data every other feature reads: the user's profile and assumptions, their transaction ledger, and the offline cache and mutation queue underneath both.

## User-visible scope

- Mobile-first PWA shell with an always-available collapsible menu, routing, and the sync-status surface.
- Supabase email/password sign-in, and onboarding that captures current emergency savings, recurring work costs and essential household expenses.
- A transaction ledger: dated income and cost records that can be created, edited and deleted. A transaction may carry an optional inclusive `occurredUntil` end date, up to 366 days, whose amount is spread evenly across every calendar day in the range.
- The transaction ledger replaced the weekly-entry form as the input path. Weeks are now derived from transactions by `adaptTransactions`, so the user records what actually happened on a date rather than maintaining a weekly summary. The weekly-entry API and tables remain for stored history and their revision/conflict semantics, but no screen writes them.
- Profile screen holding financial details display-first, with an edit toggle, and a disclosure for correcting the emergency-fund starting balance.
- Cached bootstrap data and ordered optimistic writes in IndexedDB. Reconnecting replays the queue in order using mutation UUIDs as idempotency keys.
- Visible offline state, and queued / failed / conflicted states when a mutation actually fails. A revision conflict offers "Use server" and "Keep mine".
- Destructive demo reset requires an explicit confirmation header and an online connection.

**Not in scope:** CSV import (built and then retired), OCR, bank or platform integrations, direct browser access to the database, and deployment.

## Shared contracts other features depend on

- All money crossing a JSON or SQL boundary is integer Singapore-dollar cents (`bigint` in PostgreSQL, a bounded integer in Pydantic, `number` in TypeScript). UI decimal strings are converted at the edge.
- Weeks start on Monday and use ISO `YYYY-MM-DD`. Timestamps are timezone-aware ISO strings; calendar days are Singapore-local.
- IDs are UUIDs, generated by the client so offline creation is possible.
- The API base path is `/api/v1`. Errors use `{ error: { code, message, fieldErrors?, details?, requestId } }`.
- Weekly writes accept `expectedRevision`; a mismatch returns `409 REVISION_CONFLICT` with the current server record. `Idempotency-Key` accepts a UUID.
- The committed source of truth is [`contracts/openapi/openapi.json`](../../contracts/openapi/openapi.json). Regenerate [`frontend/src/types/api.generated.ts`](../../frontend/src/types/api.generated.ts) after any backend schema change.
- Synthetic integration fixtures live under `contracts/fixtures/`. Never replace them with real financial data.

## Endpoints

All under `/api/v1`. Every route resolves the caller through the verified Supabase subject; a record belonging to another user answers `404`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/foundation/bootstrap` | Profile, assumptions, recent weeks, transactions, derived emergency-fund balance |
| PUT | `/foundation/onboarding` | Atomic initial foundation save |
| PATCH | `/foundation/profile` | Profile and emergency-savings assumption |
| PUT/DELETE | `/foundation/recurring-work-costs/{id}` | Recurring work-cost CRUD |
| PUT/DELETE | `/foundation/essential-expenses/{id}` | Essential-expense CRUD |
| GET | `/foundation/weeks` | Cursor-ready weekly history (`before`, `limit`) |
| GET/PUT/DELETE | `/foundation/weeks/{weekStart}` | Weekly-entry CRUD and revisions |
| POST | `/foundation/transactions` | Create a transaction |
| PATCH/DELETE | `/foundation/transactions/{id}` | Edit or remove a transaction |
| DELETE | `/foundation/data` | Confirmed account reset |

`profile.emergencyFundBalanceCents` is the derived balance and is what screens show. `profile.latestEmergencySavingsCents` is the raw stored opening balance. The distinction is defined in [`emergency-fund-model.md`](./emergency-fund-model.md).

## PostgreSQL foundation

The private `resilience` schema holds:

- Foundation: `profiles`, `recurring_work_costs`, `essential_expenses`, `weekly_entries`, `weekly_earnings`, `weekly_variable_costs`, `weekly_input_snapshots`, `emergency_savings_snapshots`, `transactions`, `idempotency_receipts`.
- Emergency Fund: `emergency_fund_plans`, `emergency_fund_contributions`.
- Savings Goals: `goals`, `goal_contributions`.
- Integration envelopes not yet written to: `scenarios`, `scheme_rule_versions`.

Foreign-key and filter indexes, uniqueness, category/cadence/status checks, Monday checks, non-negative money checks, the 366-day transaction-range cap, timestamps and update triggers are all in the migrations. RLS is enabled on every application table, all access is revoked from `public`, `anon` and `authenticated`, and no Data API schema is exposed. The backend connects as a trusted database role and enforces ownership in the API layer.

**Follow-up:** end-user RLS policies matching the verified Supabase Auth subject are still to be written. Until then, ownership rests entirely on the API layer.

## Offline behaviour

`frontend/src/lib/offline.ts` holds a Dexie database, `resilience-foundation`, with a cached bootstrap per owner and a `mutations` table. Mutations record method, path, body, creation time and status, and are replayed in creation order. Because the queue is ordered, one failed mutation holds the ones behind it — deliberately, since a later write may depend on an earlier one.

Two failure modes found in real use and fixed:

- Changing the date on an existing weekly entry cloned its child IDs, so PostgreSQL rejected the duplicate key. New-date saves now generate fresh IDs, the client repairs old queued mutations whose IDs collide with server data before replaying them, and the API returns a typed `409` instead of an unhandled `500`.
- A stale cached bootstrap predating `emergencyFundBalanceCents` rendered a fabricated `S$0.00`. Bumping the Dexie version now discards stale bootstraps outright rather than patching around them.

## Setup and environment

Setup, the environment-variable tables and the local runbook live in the [root README](../../README.md). Nothing in this document repeats them.

For the shared hosted database, distribute outside Git and chat: Supabase project membership per teammate, the project reference through the team setup note, and a backend-only `DATABASE_URL` — preferably the transaction-pooler URI with `sslmode=require` and conservative `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`. Never share database passwords, secret or service-role keys, personal access tokens, or login verification codes.

Apply schema only through committed migrations. One coordinated, authenticated teammate runs `npx supabase migration list --linked`, then `db push --dry-run`, then `db push`. Do not use `--include-seed` on a shared project, and never `db reset --linked` against a non-throwaway project.

## Verification performed

- Frontend: the integrated suite and the production PWA build pass.
- Backend: the integrated suite passes, including the database-backed tests with `RUN_DATABASE_TESTS=1`; Ruff clean.
- Database: local Supabase starts, migrations plus the synthetic seed apply, the pgTAP assertions pass, and `supabase db lint --local --level warning` reports no errors.
- Integration: real FastAPI → SQLAlchemy/psycopg → local Supabase bootstrap, weekly create, revision conflict, read and cleanup.
- Hosted Supabase: migration parity confirmed; RLS enabled on every application table; `anon` schema usage and `authenticated` weekly-entry SELECT both denied; remote security and performance advisors clean.
- A real `500` was found and fixed by live probing: the bootstrap created a profile without committing it, and the essential-expense and recurring-cost writes never ensured one, so a new user's first write failed a foreign key. Both paths are covered by database-backed regression tests.

## Limitations

- Ownership is enforced in the API layer, not by RLS policies.
- Weekly entries and the transaction ledger coexist in the schema and the API, but only the ledger has a UI. The weekly-entry endpoints are effectively unused by the client and their revision-conflict path is now exercised only by tests.
- Any feature adding a table must include `user_id`, ownership indexes and constraints, RLS posture, migration tests, and a regenerated API contract where exposed.
