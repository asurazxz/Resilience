# Feature 1 — Foundation Input

**Implemented:** 2026-09-02
**Branch:** `feature/01-foundation-input`
**Status:** Runnable; locally and remotely verified on Supabase

## User-visible scope

- Mobile-first PWA shell with overview, weekly history, CSV import, and assumptions navigation.
- Anonymous demo onboarding for emergency savings, recurring work costs, and essential household expenses.
- Editable weekly earnings and variable work costs, including explicit no-income weeks.
- Strict Resilience CSV download, server-side validation preview, and user-confirmed conversion into weekly entries.
- Cached bootstrap data and ordered optimistic writes in IndexedDB. Reconnect triggers replay using mutation UUIDs as idempotency keys.
- Visible online/offline and queued/failed/conflicted states. Revision conflicts offer “Use server” and “Keep mine.”
- Destructive demo reset requires an explicit confirmation header and an online connection.

OCR, user authentication, deployment, bank/platform integrations, and direct browser access to Supabase are deferred. The overview's remainder is a simple orientation estimate; Feature 2 owns production financial calculations and explanations.

## Shared contracts other features depend on

- All money crossing JSON or SQL boundaries is integer Singapore-dollar cents (`bigint` in PostgreSQL, bounded integer in Pydantic, `number` in TypeScript). UI decimal strings are converted at the edge.
- Weeks start on Monday and use ISO `YYYY-MM-DD`. Timestamps are timezone-aware ISO strings; the demo profile timezone is `Asia/Singapore`.
- IDs are UUIDs generated by the client when offline creation must be possible.
- API base path is `/api/v1`; machine-readable errors use `{ error: { code, message, fieldErrors?, details?, requestId } }`.
- Weekly writes accept `expectedRevision`; mismatches return `409 REVISION_CONFLICT` with the current server record. `Idempotency-Key` accepts a UUID.
- The committed source of truth is [`contracts/openapi/openapi.json`](../../contracts/openapi/openapi.json). Regenerate [`frontend/src/types/api.generated.ts`](../../frontend/src/types/api.generated.ts) after backend schema changes.
- Synthetic integration fixtures are under `contracts/fixtures/`. Never replace them with real financial data.

## PostgreSQL foundation

The private `resilience` schema contains:

- Feature 1: `profiles`, `recurring_work_costs`, `essential_expenses`, `weekly_entries`, `weekly_earnings`, `weekly_variable_costs`, `weekly_input_snapshots`, `emergency_savings_snapshots`, and `idempotency_receipts`.
- Feature 3 integration envelope: `goals`, `goal_contributions`.
- Feature 5 integration envelope: `scenarios`.
- Feature 4 integration envelope: `scheme_rule_versions` with JSON rule payload, effective dates, official source, and review date.

Foreign-key/filter indexes, uniqueness, category/cadence/status checks, Monday checks, non-negative money checks, timestamps, and update triggers are in the migration. RLS is enabled on every application table, all access is revoked from `public`, `anon`, and `authenticated`, and no Data API schema is exposed locally. The backend connects as a trusted database role. Auth/RLS policies must be designed before replacing the anonymous prototype with real users.

### Complete local runbook

From the repository root, with Docker Desktop running:

```powershell
npm install
Copy-Item frontend\.env.example frontend\.env
Copy-Item backend\.env.example backend\.env
npm run db:start
npm run db:reset
```

In a second terminal, start the API:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

In a third terminal, start the PWA:

```powershell
npm run dev:frontend
```

Open `http://localhost:5173`; use `http://localhost:8000/docs` for the API and `http://127.0.0.1:54323` for local Supabase Studio. Confirm the API is ready with `Invoke-RestMethod http://127.0.0.1:8000/ready`. Stop the API and PWA with `Ctrl+C`, then run `npm run db:stop` to stop Supabase.

The 2026-09-02 live check started this exact stack successfully, received `{"status":"ready"}` from the API, and received HTTP 200 from the PWA root.

For future migrations, one coordinated authenticated teammate should run:

```powershell
npx supabase migration list --linked
npx supabase db push --dry-run
npx supabase db push
```

Do not use `--include-seed` for normal shared-project pushes. Never use `db reset --linked` against a non-throwaway project.
